02 · The finding that constrains every other finding

Two revisions were the same agent, and scored four points apart

Revision v5 added a loop-level guard to v4. The guard fired zero times in 189 graded runs, which means every one of those runs executed exactly the code v4 executed. The two arms are behaviourally identical, so their scores are two samples of one agent.

That is the same size as most of the differences the report had been discussing, so it retired an earlier published result of +1 point and set a floor: read the per-task column, and treat any aggregate gap under roughly five points as absent.

It is one observation per suite rather than a distribution, so it does not establish a noise floor. It does establish that differences of this size arise with no behavioural change at all.

03 · Engineering

A prompt instruction is not a mechanism

Revision v1's prompt already said "Do not ask for permission yourself." The model ignored it on five of five runs of the relevant task. Of v1's 23 failed runs, 17 were the agent asking a question where it had enough information to act — in a driving context, every unnecessary question is a turn the driver must process at speed. Four reproducible clusters, one root cause. Each fix below moves a guarantee out of prompt text and into code.

Confirmation gate

In a static table, not in the prompt

Risk tier is a property of the tool, decided in code. The commit call takes no arguments, so what executes is what was frozen when it was proposed, not whatever the model said afterwards. An unclassified tool fails closed to external-write.

Return shape

An empty list reads as "there is none"

Availability returning [] for a fully booked hour and coursework returning [] for a day whose work came due two hours ago are the same defect. Both were fixed by changing what the tool returns, not by adding a prompt line.

Grading

Three deterministic graders, no judge

End-state difference, trajectory, and response. Proposed and executed tool calls are recorded as distinct events, which is what makes the unauthorized-side-effect rate computable at all: a blocked proposal and a completed execution are different rows.

Reproducibility

Six independently versioned components

Prompt, tool schema, agent loop, confirmation policy, task set, environment snapshot. Any published arm is re-derivable from the command line, and tests pin the older prompt text so a later edit cannot silently rewrite history.

Harness robustness

Infrastructure faults leave the denominator

A provider rate limit destroyed 84 of 120 runs and took the batch with it. Failed runs now go to an error log and out of the denominator, because scoring an infrastructure error as a task failure biases task success downward.

One agent, not two

No evaluation-only code path

The benchmark calls the same constructor the shipped command-line entry point calls, so a number in the report is a number about the product.

04 · Retrieval

Handed three unrelated stories, it read them out anyway

A driver asks two different questions with one tool. "Any tech news today?" contains no subject at all, so relevance ranking has nothing to score and every document ties. "Anything about OpenAI?" is the opposite: the newest three stories are rarely the ones about OpenAI, and answering with them is the same defect as before — a non-empty reply concealing an empty result.

So retrieval branches on whether the query names a subject. The baseline that does not branch is the one worth measuring against, because it is what adding retrieval usually means: fetch the feed, ignore the question, summarise the newest items. It was run as an arm rather than dismissed.

The two arms are identical on open-ended questions. That is the control: they differ only where the branch is the thing being tested, and the named-subject intervals do not overlap.

The zero is the finding. With no triage the agent said "there are no recent news articles specifically about OpenAI" — correct — and then read out the three unrelated stories it had been handed, on four runs of five. On the fifth it offered to. The model did not lie; it reported the absence and then could not leave the material unused. The fix is not to ask it to stay silent, but to not hand it the stories.

Grounding grader

Checked against what it retrieved, not against a list

Every name and figure spoken must appear in that run's own tool results or in the driver's own words. No corpus, no labels, no language-model judge — the reference set is already in the trajectory. It replaces forbidden-string rules, which can only catch the false statements somebody predicted.

What it caught

True in the world, absent from the retrieval

The baseline arm said "Nvidia's CEO, Jensen Huang" having retrieved three stories that never mention a CEO. Correct, and ungrounded. Grounding is a necessary condition for a truthful summary, never a sufficient one: "Nvidia acquired Anthropic" passes if both names were retrieved, and a test asserts that limitation.

The grader had a bug

Found by the ablation, fixed, re-graded for free

Possessives and hyphenated compounds were scored as fabrications. The unit test meant to cover it had passed by accident. Because the graders are deterministic, the fix was re-scored from stored trajectories with no further model calls — and the headline rates did not move, because the spurious failures shared runs with real ones.

Frozen world

A live feed cannot appear in a graded run

Two arms an hour apart would face different facts. The evaluated corpus is one real read of a public feed, hashed by content and re-verified on load, so an edited corpus fails construction instead of quietly producing incomparable numbers. Production parses the same bytes through the same parser.

05 · In production

True, and the opposite of useful

The agent runs on a deployed telephony endpoint reading a live calendar, mailbox and university coursework feed. At 07:00 one morning it produced this:

Driver"What is due today and what is on my calendar?"
Hisho"Nothing is due today. You have one event: volunteering [organisation redacted], from 9:30 AM to 6:30 PM."

Two assignments had come due at 05:00 that morning. The query filtered on now <= due_at <= horizon, so "nothing is due today" was the only answer the data could produce.

Widening the window alone would have been worse than the defect. The coursework feed carries no submission state, so every item reports as unsubmitted whether or not it was handed in. An agent that simply surfaced those two items would have told the driver they had missed two deadlines they may well have met — on every drive, for as long as the items stayed in the window. A false alarm that repeats is worse than a false negative that is silent.

So the report carries a submission_known flag, and the same code speaks in two tones depending on what the source can support. Against the live feed it now says: "2 came due in the last 24 hours. This source cannot tell whether they were submitted, so ask whether they went in — do not say they were missed." The honest sentence lives in the data, not in a prompt line the model may or may not weight.

Unmeasured  15 offline tests, 7 of which fail without the change, verified by reverting each half separately. No benchmark arm has been run on it, so there is no task-success figure for it and none should be inferred.

06 · Summary

What this project demonstrates

Four claims, each one measured. Every figure below is reproducible from the command line against the same fixtures.

Resume entry

Hisho — Hands-Free Driving Voice Agent | Python, FastAPI, OpenAI API, pytest, Railway

  • Designed an agent evaluation harness measuring 1,112 graded runs across 5 agent revisions, 2 retrieval policies and 3 task suites, reporting 10 metrics with sample size and Wilson 95-percent confidence intervals on every rate.
  • Improved held-out task success from 0.51 to 0.81 with non-overlapping confidence intervals by revising only prompt and tool-description text, holding model, agent loop and environment fixtures constant.
  • Benchmarked a retrieval-augmented generation (RAG) tool against a no-triage baseline on a content-hashed corpus, raising task success from 0.77 to 1.00 and correct reporting of an empty retrieval from 0 of 5 to 5 of 5, scored by a deterministic grounding check requiring every entity spoken to appear in that run's retrieved documents.
  • Determined the harness noise floor by identifying two revisions as one unchanged agent scoring 2 and 4 points apart, retiring a prior 1-point result and setting a 5-point significance threshold for later claims.

Deliberately excludes voice latency, streaming audio and context engineering, which a companion project already covers. What this entry adds is measurement: held-out generalisation, a measured retrieval ablation, and a stated noise floor. A fifth bullet is available and sometimes worth the swap — the confirmation gate was moved out of prompt text into a static risk table with a zero-argument commit call, holding unauthorised side effects at zero across all 1,042 benchmark runs and three prompt revisions.

07 · Limitations

The things to raise before someone else does

The full report lists twelve. These are the ones that bound what the numbers above can be claimed to mean.

  1. The held-out set cannot separate difficulty from fitting. Both arms drop from development to held-out, so the gap is an upper bound on overfitting, not a measurement of it. The within-column comparison, 0.51 against 0.81, does not depend on that caveat.
  2. The held-out set has since been consumed. Revision v4 was written against two of its fourteen tasks, so from v4 onward there is no held-out set and 0.87 is a development number. A fresh set is the top open item.
  3. n=5 per task, and the v4/v5 accident puts a number on what that buys. Raising n is the cheapest real improvement available to this harness.
  4. One model. Everything is gpt-4o at temperature 0.2. Whether these prompt changes help a different model is unmeasured.
  5. The gate-off control arm was never run. An advisory policy mode exists and is wired. Until it runs, a rate of 1.00 is consistent with "the gate works" and with "this model never tried", though v1's traces argue against the latter.
  6. Response grading is substring rules, so false-claim detection catches only the claims that were thought to forbid. This is the gap the grounding method in section 05 is designed to close.
  7. The benchmark world is a mock, and there is no speech recognition in the loop. The most likely real-world failure — mishearing one contact's name for another — is not represented anywhere in 1,042 runs. No number here is a statement about production readiness.
